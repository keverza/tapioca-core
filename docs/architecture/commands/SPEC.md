## Scope

`internal work item` owns Python workflows, command ports, Python-facing task flows, and the
metadata that defines command controls. It does not own native SDK workarounds, the
controlled API boundary, rendering engines, analysis contracts, or evaluation services.

The public product name is Tapioca. `EvP` remains the compatibility-critical internal name:
the add-on binary, source directory, bus compatibility verbs, and the `evp` Python package
remain valid. New commands should use `import tapioca`; existing `import evp` commands remain
valid.

## Runtime Contract

The command path is:

```text
palette -> AST scan -> DG controls -> worker command
        -> tapioca.api.call -> Layer-1 bus -> MainThreadGate -> ACAPI
```

- Python owns workflow composition, pure algorithms, and command-level policy.
- C++ owns Archicad integration, DG UI, thread marshaling, native geometry, and transport.
- Python may compute off the main thread, but it never calls ACAPI directly.
- Native UI is rendered by Archicad DG. Commands do not create tkinter, Qt, or other Python UI.
- The public API is versioned through `evp.API_VERSION` and the `tapioca` compatibility shell.
- A command never becomes a second runtime for Notebook, WebUI, or another consumer. Those
  consumers invoke the same command and API surfaces.

## Command Authoring

The repository copies under `AddOn/EvP/Commands/` and `AddOn/EvP/Diagnostics/` are the source
of truth. The deployed copy in `%LOCALAPPDATA%\Tapioca\Commands` is generated by the one-way
sync and must never be edited directly.

A production command has at least:

```text
AddOn/EvP/Commands/<Name>/
  command.py
  helpers.py        # optional, command-local
```

The entry file is scanner-readable and follows this shape:

```python
import tapioca

@tapioca.command(
    title="Your Command",
    category="Annotation",
    needs_selection=True,
    description="One line for the palette.",
)
def run(count: tapioca.Int(minimum=1) = 4, dry_run: bool = True):
    ...
```

Entry-file rules:

- The import is `tapioca` or the compatibility form `evp`.
- Decorator and annotation arguments that the palette reads are literals. The one
  exception is `inputs=`/`outputs=`/`plan=`, which name a class or function in the
  module; the scanner records the identifier and refuses a computed value.
- The entry point is a top-level `run` function.
- Helpers may use ordinary Python, but must not bypass the `evp` API boundary.
- `needs_selection=True` and required parameters are enforced by the palette before Run.
- Destructive commands default to `dry_run=True`, log their proposed changes, and batch real
  writes in one transaction.
- A command logs useful detail to `evp.paths`; an alert contains only a short instruction.

### Schema-Declared Ports

A command may declare its ports as a Pydantic model instead of as `run()`
annotations. Both forms are supported and neither is deprecated; the model form
exists because annotations cannot carry a declared return type, per-parameter help,
or a constraint that is also enforced.

```python
class Inputs(NodeModel):
    spacing: float = Field(default=1.0, gt=0, title="Spacing",
                           description="Shown as help under the row.",
                           json_schema_extra=port(unit="m"))

@tapioca.command(title="...", inputs=Inputs, outputs=Outputs, plan=plan)
def run(ctx, inputs):
    ...
```

- A field's `title=` is its palette label. A field without one falls back to the
  parameter name; pydantic's generated title is not used, because it would give the
  schema form display text the signature form never had. `Field(description=...)`
  documents the model and reaches other consumers, but the palette does not draw
  it — a help line under every row roughly doubled the parameter block's height.
- `run(ctx, inputs)` is the required signature. Annotating it as well would give one
  control two sources, and nothing downstream could resolve which the palette drew.
- Ports reach the palette in the same flat per-parameter shape the AST pass emits.
  `evp._ports` performs the translation and `AddOn/EvP/tests/test_ports.py` asserts
  the two paths are byte-equal for an equivalent declaration.
- The palette does not import command modules. `evp._schemagen` imports one folder
  in a subprocess and `evp._schemacache` caches the result against a content hash of
  the folder's `.py` files. A generation failure is a scan diagnostic; identity still
  comes from the AST, so a command whose import fails is still listed with its error.
- `evp._invoke` is the single place that decides between the two calling
  conventions. All three runners — embedded, external, and the offline harness —
  call it.

### Plan and Preview

`tapioca.Plan` is an ordered, immutable set of intended writes (`ElementSpec`), each
naming a bus verb, its parameters, and a stable `key`. A Plan is built by the
`plan=` callable, which reads and computes but never writes. The same object renders
as a table, diffs against a previous Plan, and replays into one `evp.transaction`.

- `ElementSpec.key` is the identity a diff compares across runs. It is derived from
  the element, never from a loop counter.
- `Plan.commit()` opens exactly one transaction, so the existing one-undo-step,
  all-or-nothing contract is unchanged. `Plan` sits above `evp.transaction`; it does
  not replace it.
- A Plan is not a promise. The model can change between building and committing, so
  a run reports what `commit()` returned, never the Plan's contents.
- The runtime builds the Plan once, before `run()`, and hands it over as `ctx.plan`.
  A command does not call its own planner again: a second call after a commit reads
  a model that already contains the writes.
- `ctx.previous_plan` is the last completed run's Plan, persisted by
  `evp._planstore` under `evp.paths.cache_dir`. Module state cannot hold it —
  `evp._commandpath` evicts every module under the scripts root after each run and
  the external runner is a new process. A preview does not move that baseline.
- The preview band that renders a Plan is `internal work item`/`internal work item` and is
  not built yet; a command shows its diff as TEXT through `ctx.show()` until it is.
  `evp.ui.table` is not an option: it drops or misplaces cell text after the first
  fill (`CMD-ResultsTableColumns`, reconfirmed in Archicad 2026-08-19), and the
  panel is a proportional font, so no result surface pads columns.
- Anything only the user can answer belongs in `ctx.show(questions=[...])`, which
  renders it as the panel's last section. A probe whose questions reach only the log
  asks them after the looking is over.

### Modes and Conditional Inputs

`tapioca.Action` is the canonical mode selector. `show_when` may be attached to any
parameterized annotation and may be controlled by an Action, Enum, or bool.

```python
def run(
    action: tapioca.Action("Place", "Update", "Remove") = "Place",
    layer: tapioca.Layer(show_when={"action": ["Place", "Update"]}) = "Annotation",
    radius: tapioca.Float(unit="m", show_when={"action": "Place"}) = 1.0,
    dry_run: bool = True,
):
    ...
```

Hidden values are still passed to `run`; visibility never changes the function signature.
A hidden required parameter never disables Run. The scanner rejects an unresolved controller,
an impossible value, multiple controllers, or a second Action. That failure is diagnostic, not
silent omission.

### Selection Sets

Commands that need independent element groups declare literal role names with
`selection_sets=("Targets", "Operators")`. The session-only selection manager owns capture,
add, remove, clear, and reselect operations. It is not project data and is cleared when the
selected command changes or the palette closes.

`evp.selection.sets` exposes `get`, `update`, `add`, `remove`, `clear`, `info`, `names`, and
`reselect`. A command may only access roles declared by its active metadata. GUIDs are normalized
at the Python edge with `strip("{}").upper()` while capture order is retained.

## Execution and Failure Rules

- Reads use `raise_on_error=False` when absence is an ordinary result; writes let `EvpError`
  propagate.
- Batch writes in one `evp.transaction()` so the user receives one undo step and one gate batch.
- Native commands do not open undo scopes. The dispatcher owns immediate write scopes and
  transaction replay.
- Long pure-Python loops call `evp.runtime.check_cancel()` between chunks.
- Cancellation is enforced at the bus boundary. An in-flight ACAPI call is not interrupted;
  a cancelled command is a clean cancelled outcome, not a failed run.
- A command that leaves highlights or temporary view state clears it in `finally` unless it
  explicitly implements the future residual-cleanup contract.
- Exact parameters sent to the bus are part of diagnostic evidence. A prose summary is not a
  substitute for the serialized parameter dictionary.

## Shared Imports and Deployment

Command import precedence is:

1. The command's own folder.
2. `Commands/_lib/` for shared modules, deployed at the flat target root.
3. An exporting sibling folder containing `_exports.py`.

The command path is managed centrally by `evp._commandpath`; commands must not use ad-hoc
relative `sys.path` insertion to import sibling commands. `_lib` is skipped by the scanner so
its files cannot register commands.

The deployment contract is:

```powershell
cd AddOn\EvP
.\Sync-Commands.ps1
```

Then the user presses Rescan. `Sync-Commands.ps1` composes the roots listed in
`AddOn/EvP/command-sync.json`, copies only runtime files, and keeps the target flat. It
records its owned top-level folders in `.tapioca-sync-state.json`; `-Prune` removes only
folders from that record that are no longer active. Edits under `Sources/PyPackage/evp/`
require a native rebuild before they are visible in Archicad.

## UI and Progress

The palette reads metadata without executing command code. `ControlPalette` owns DG events,
the vertical layout bands, splitters, and run orchestration. Parameter controls belong to
`Palette/ParamPanel`; results belong to `Palette/ResultsTable`; selection roles belong to their
own panel. Sub-objects place themselves through `PlaceAt` and do not attach themselves as
observers.

`evp.ui.progress` and `evp.ui.stages` are the command-side progress contract. Stage boundaries
are explicit and throttled progress is safe in per-item loops. A final status message cannot be
the only evidence because the palette replaces it when the run finishes; durable detail goes to
the command log.

The results table keeps content-derived widths for initial layout. User header widths must be
preserved and applied to the corresponding row fields; the generic header/data synchronization
work is tracked separately as `internal work item`.

## Output and Evidence

Commands write only below `%LOCALAPPDATA%\Tapioca`, using `evp.paths`:

- `logs` are append-only, capped, and rotated;
- `output` is the latest artifact and may be overwritten;
- `dumps` are timestamped per run and are never overwritten.

`DumpTestCase` captures focused real Archicad selections, raw responses, geometry, metadata,
and relevant context for offline tests. Geometry algorithms are not validated against synthetic
input alone. A probe isolates one empirical question, records a `NOW LOOK / REPORT` instruction,
and remains as a regression fixture or is archived under the probe lifecycle policy.

The offline gate for a command is:

```powershell
python tools/quality/check_python.py
python AddOn/EvP/tests/dryrun_command.py AddOn/EvP/Commands/<Name>
python -m py_compile AddOn/EvP/Commands/<Name>/command.py
```

Native or package changes additionally require the relevant architecture checks, C++ tests,
and a rebuild. Live Archicad evidence is recorded in the owning task, not inferred from a
successful scanner or dry run.

## Release and Devkit Contract

The release task `E-14` belongs to `internal work item`, but its command-facing contract is fixed
here so packaging cannot change command semantics:

- A release contains the add-on, its Python package, the compatible Tapir add-on, and only
  commands explicitly marked for production. Probes, archives, tests, fixtures, and handoffs
  never enter the production command root.
- The installed command root remains flat to the runtime scanner. A `devkit` subdirectory may
  sit beside it because it contains no scanner entry file.
- The devkit carries agent-facing JSON schemas for native Tapioca and Tapir commands, examples,
  cleaned author rules, and the API reference. Human website HTML is not an agent source.
- Native schemas are generated from the same registered command implementation that ships in the
  add-on. Hand-maintained sidecar schemas and regex scraping of C++ are not release mechanisms.
- A new command passes three gates: handoff/specification, offline implementation plus live
  verification, then a production-release flag and production-only sync. Unverified commands
  remain diagnostics or probes.
- Runtime provisioning is installer work. Per-command requirements remain declared metadata and
  are resolved by the managed runtime; the installer does not silently modify a user's external
  Python environment.

## Ownership Handoffs

- Native SDK capabilities belong to `internal work item`; command folders request them instead of adding
  local ACAPI workarounds.
- Rendering and viewer caches belong to `internal work item`.
- Browser UI and viewer consumers belong to `internal work item`.
- Sun, shadow, heatmap, and feasibility result semantics belong to `internal work item`.
- Scoped scene packaging belongs to `internal work item`.
- Installation, runtime provisioning, release packaging, and quality tooling belong to
  `internal work item`.

Cross-initiative gaps are represented once in the provider registry and referenced by the
consumer task's `blocked_by`; a command does not duplicate a provider implementation.
